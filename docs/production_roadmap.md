# AI Novel System v2 后续开发方案

本项目下一阶段的目标不是继续增加流程按钮，而是把系统从“生产流水线控制台”收敛成“作者省心的主笔助手”。

## 总目标

用户只做作者判断：

- 设定作品方向
- 阅读当前可用稿
- 选择通过、局部改、整章重写

系统承担内部流程：

- 骨架、brief、导演单
- 草稿、质检、必要修订
- 连续性回写、可审批状态判断
- 失败诊断与成本记录

## 开发原则

1. 日常前台不暴露内部流程名。
2. 规则质检只阻断硬问题，软问题交给主编审稿和人工判断。
3. 正文生成优先使用短导演单，不把长骨架、旧质检、旧稿和人工意见全部塞进 prompt。
4. 修订必须区分“局部改”和“整章重写”。
5. 模型连续失败或自动修订达到上限时，停止烧 token，要求人工重新给方向。
6. 对“游戏世界是真实异世界”的作品，系统必须优先保护世界真实感：玩家进入游戏等同穿越到另一个有历史、门派、人情、规则和利益冲突的世界；成长来自遵守世界规则、修炼、拜师、交易、冒险和承担后果，而不是机械打怪升级、刷副本或完成系统任务。
7. 任何“生产方向不对”的问题，先做方向对齐审计，再决定是否改地基、改 brief、改 prompt、换模型或重写正文；不能长期依赖人工手工代修数据库。

## 阶段一：主笔模式稳定化

目标：点击一次，稳定产出“可读稿 / 需要人工方向 / 系统失败原因”。

- 固化主笔循环：brief -> draft -> review -> revise -> review -> continuity -> wait_approval。
- 主笔模式只返回三种终态：
  - ready_for_human_reading
  - needs_author_direction
  - system_failed
- 自动修订默认 2-3 轮。
- 前台用人话显示后台结果，不显示内部动作链。

## 阶段二：章节导演单

目标：提升内容稳定性，减少 prompt 噪声。

- 每章生成前先构造短导演单。
- 导演单包含：
  - 前章最后状态
  - 本章开场
  - 6-8 个小单元
  - 必须兑现的爽点、代价、钩子
  - 禁止事项
- 正文生成主要看导演单、前章摘要、关键 Canon。
- 质检建议不能原样进入下一轮正文 prompt，必须先转译为可执行改写任务。

## 阶段三：前台体验重排

目标：让 dashboard 像写作台，不像后台管理系统。

保留四个主页面：

- 写作台
- 作品设定
- 章节地图
- 后台诊断

后台诊断默认折叠，不参与日常写作。

## 阶段四：质量样本集

目标：让 prompt 和流程修改可回归验证。

- 建立固定测试书与前三章样本。
- 每次改动后记录：
  - 字数
  - 前章承接
  - 主编评分
  - 人工可读等级
  - 是否重复旧稿

## 阶段五：多模型策略

目标：降低成本，提高稳定性。

- 便宜/快模型：骨架、brief、导演单、质检初筛。
- 强模型：正文草稿、整章重写、主编审稿。
- 低温任务降低 temperature，高创造任务适度放宽。

## 阶段六：方向对齐诊断

目标：让作者能自己判断系统为什么写偏，而不是每次等待人工手工排查。

- 建立 StoryFoundation / StoryBible / WorldRule / PowerSystem / ChapterBrief / 最新正文的方向对齐审计。
- 审计输出：
  - 核心设定源是否写入作者意图
  - 最新章节 brief 是否承接作者意图
  - 是否残留旧质检、旧修订合同、旧桥段要求
  - 最新正文是否出现反方向写法
- 前台继续生产前应能提示：
  - 需要先改生产骨架
  - 需要先清理章节 brief
  - 需要 fresh 重写
  - 可以继续生产

详细根因分析见 [`docs/root_cause_alignment.md`](root_cause_alignment.md)。

## 阶段七：生产闭环治理

目标：把“写偏了怎么办”从人工猜测变成系统判断。

- 生产前：裁剪上下文，只给模型当前章需要的短导演单、前章承接、关键 Canon 和作者口味。
- 生产中：区分草稿、局部补丁、定点修订、结构重写、按骨架重启，避免所有重写按钮实际都变成“整章再写一遍”。
- 局部补丁：如果只是命中明确偏差词，优先确定性替换并复检，不调用模型重写整章。
- 生产后：同时做规则质检、模型偏差检查、作者意图验收。
- 前台：显示失败归因和下一步动作，而不是只显示“质检未通过”。
- 人工介入：作者只需要选择“通过 / 局部改 / 整章重写 / 改骨架”，不需要理解数据库状态和内部任务链。

## 阶段八：生产总控层

目标：让系统先做整体研判，再决定下一步，而不是让作者在多个后台面板之间判断。

- 总控输入：生产准备度、章节计划、人工等待项、后台队列、方向对齐审计。
- 总控输出：
  - `blocked`：先处理阻断，不继续消耗正文 token。
  - `running` / `queued`：等待或启动后台任务。
  - `needs_author`：内容已到人工判断点，作者只读稿并决策。
  - `can_produce`：可以继续生产下一章。
  - `idle`：当前范围没有动作。
- 前台首页优先显示总控判断，再显示细节诊断。
- 旧的后台命令建议必须服从总控建议，避免同一页面出现两套下一步。

## 阶段九：质量、模型、数据与发布治理

目标：让系统能持续稳定，而不是每次靠现场感觉判断。

- 可读性专项：质检报告加入开场吸引力、主角主动性、场景连续、对话活性、感官具体、爽点具体和章末追读维度。
- 样本回归：固定样本集检查字数、质检、可读性、作者意图和模型偏差词，作为每次改动后的回归哨兵。
- 模型策略：按规划、正文、修订、审稿、局部补丁分层展示模型角色和风险；局部补丁优先不用模型。
- 数据治理：审计最新 brief 是否混入旧质检、旧修订合同、旧验收清单，保持“历史归历史，当前生产材料归当前”。
- 发布前预检：发布任务显示标题、字数、元信息泄露、偏差词和导出预览，避免不合格正文进入平台链路。
